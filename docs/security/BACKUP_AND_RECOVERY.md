# SEC-01 backup and recovery plan

No verified production backup or restore drill has been demonstrated in this review. [Supabase documents](https://supabase.com/docs/guides/platform/backups) daily managed backups for Pro/Team/Enterprise, recommends regular off-site `supabase db dump` exports for Free projects, and states that database backups contain Storage metadata **not object bytes**. Do not assume free-tier point-in-time recovery. Confirm this project's actual plan and hosting settings before launch. [Vercel documents](https://vercel.com/docs/cli/rollback) Hobby rollback to only the immediately previous production deployment; code rollback is not a database/storage restore.

Inventory: Postgres schema and data (including `auth` linkage, package definitions, profile children, file/document records, audit events); both private Storage buckets and object metadata; deployment environment/secrets (in secret manager, never in a plaintext archive); code, lockfile and ordered migrations; DNS/domain and Supabase Auth redirect configuration. Database dump alone does **not** contain Storage bytes. Preserve access controls and encryption on backup exports.

Proposed targets, not guarantees: RPO ≤ 24 hours and RTO ≤ 48 hours for an initial V1 service. These need budget/owner approval and a timed restore drill. Use a separate test project for restore, then verify FK counts, role/profile linkage, bucket objects, login, document generation and private-download denial. Record timestamp, data loss and defects. Define retention of backups separately from candidate retention; restrict backup access and test deletion.

Partial-failure playbook: disable affected mutations; inspect account provisioning reconciliation, file pointer/history and orphaned objects; restore from known checkpoint only after owner approval; never casually replay a destructive migration. New migration is prepared but unapplied. Rate-limit/audit structures must be included in future backup/restore procedures.
