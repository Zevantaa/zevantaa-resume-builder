# CI/CD security gates

`.github/workflows/quality-security.yml` runs on PRs and pushes to `develop`/`main` with read-only repository permission, Node 22, `npm ci`, local configuration validation, secret-pattern scan, tests, lint, build, production-dependency `npm audit --omit=dev`, whitespace check and CycloneDX production SBOM artifact (30-day retention). The production audit **hard-fails** on known vulnerabilities. A separate full `npm audit --json` step remains visible but is non-blocking only while its known findings are development-only; its unaltered JSON is retained as a 30-day artifact for human review. Any new full-audit finding must be classified, and any production finding remains a hard failure. No Supabase secret is provided to CI. The local environment check is deliberately not a production configuration attestation; run `environment:validate -- production` privately at deployment.

The pattern scan is high-confidence and limited to versioned and new non-ignored text; it does not replace provider secret scanning or inspect encrypted/binary artifacts. The full audit currently shows five High development-chain entries from unpatched `braces`, and the production audit reports zero after a pinned `argparse` override removed Mammoth's vulnerable CLI-only transitive path. See `docs/security/DEPENDENCY_AND_SUPPLY_CHAIN.md` for each original entry and review rationale. Do not call the dev finding fixed or suppress it. SBOM is a dependency inventory, not a vulnerability clearance. CI checks do not prove live Auth, Storage, CSP, recovery, RLS or restore behavior. Keep run URL, SHA, SBOM, full audit artifact and triage notes with each release record.

Recommended GitHub branch protection, **not changed remotely here**: require PR and independent review for `develop`/`main`, require `verify` check at the expected SHA, dismiss stale approvals after new commits, restrict force pushes and branch deletion, require conversation resolution, and limit bypass admins. Pin third-party Actions to reviewed commit SHAs in a later hardening pass; the current workflow uses major-version tags. Never store long-lived production credentials in pull-request secrets or print secret values in logs. Deployment remains an explicitly approved separate stage.
