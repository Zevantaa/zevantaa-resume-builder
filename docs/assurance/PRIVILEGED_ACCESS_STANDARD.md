# Privileged access standard

Owner: Sofiology security/release owner. Inventory every `admin` role, Supabase dashboard owner/admin, hosting administrator, GitHub maintainer, backup operator and holder of server-only keys; record named person, purpose, scope, grant date, approver and next review date in a restricted register. Do not put identities or recovery material in this repository. Application `admin` and `client` roles come from `public.user_roles`; URL intent never grants privilege. Service-role/secret keys are server-only and bypass normal user RLS, so restrict their deployment access.

Require MFA for all privileged provider, hosting and GitHub accounts and for master-admin app access before production. Supabase Auth supports TOTP enrollment/verification, but this project has **not** established app-level MFA enforcement or verified provider settings; do not claim it is enforced. Use a separate approved implementation/QA change before a production gate is closed. Keep the single-master-admin V1 model; do not create an extra break-glass app administrator without scope approval.

Grant least privilege for a named task, review access at least quarterly and after personnel changes, and revoke promptly on offboarding. Onboarding requires identity verification, approval, MFA enrollment, role test and inventory update. Offboarding requires role revocation, active-session review, key rotation when exposure is possible, and audit of recent privileged actions. Never share admin credentials.

Break-glass: declare incident and get two-person approval if available; use a protected provider-owner recovery path, not a hidden app bypass. Log who approved, why, start/end UTC, actions and affected resources. Time-limit emergency access, rotate temporary credentials, review logs and remove access afterward. Lost master-admin access: verify ownership through provider/hosting account recovery, preserve audit evidence, restore Auth access through the authorized Supabase administration path, re-confirm database `admin` role and MFA, then test client-role denial. Do not change `user_roles` from a browser or send credentials in URLs.
